# Balance Vault Threat Model

This document records the initial threat model. A mitigation is only marked
verified when an executable test or a PostgreSQL runtime check provides
evidence. PostgreSQL-only items remain pending until Docker is available.

| Threat | Attack scenario | Mitigation | Evidence | Residual risk |
|---|---|---|---|---|
| Password brute force | Repeated login attempts | Argon2id hashing; rate limiting remains deployment work | Password hashing is implemented; rate limiting pending | Login flooding |
| Weak password hashing | Database leak exposes weak hashes | `pwdlib` Argon2id recommended configuration | Local authentication tests pass | Operational secret/database exposure |
| JWT forgery | Attacker signs a token | Configured signing key and algorithm allow-list | Token creation/import tests pass | Secret rotation is pending |
| Expired token reuse | Old token is replayed | JWT `exp` validation | PyJWT validates expiry; runtime test pending | Revocation is not implemented |
| IDOR | User requests another user's account | Owner-scoped account queries | Protected endpoint test exists; DB integration test pending | Delegated permissions are not implemented |
| Vertical privilege escalation | Public registration requests admin role | Registration always creates Account Holder | Enforced in route code | Admin provisioning workflow pending |
| SQL injection | Malicious identifiers or payloads | SQLAlchemy bound parameters | No raw SQL for request data | Future raw SQL must remain parameterized |
| Mass assignment | Client submits privileged fields | Explicit Pydantic request schemas | Registration schema excludes role | Future schemas require the same discipline |
| Negative balance | Withdrawal races past balance check | Row locking plus database non-negative check | CI runs PostgreSQL integration checks; competing-withdrawal scenario pending | DB outage prevents posting |
| Duplicate payment | Same request is replayed | Actor-scoped idempotency key and request hash | Hash unit tests pass; PostgreSQL replay test pending | Retention policy is durable but not operationalized |
| Key reuse with changed payload | Same key, different amount | Canonical request fingerprint | Hash unit tests pass | Error monitoring pending |
| In-flight idempotency race | Duplicate arrives while first is active | Unique key and row locking | PostgreSQL concurrent test pending | Recovery of abandoned processing rows needs an operational job |
| Partial transaction failure | Failure after journal before balance update | One SQLAlchemy transaction | CI rollback test verifies uncommitted account changes are absent | Failure injection between service statements remains pending |
| Unbalanced journal | One side of a posting is missing | Two entries generated by service; journal checks pending | PostgreSQL aggregate guard pending | Posting function is future hardening |
| Ledger tampering | Update/delete historical entry | PostgreSQL append-only triggers | CI verifies trigger installation and both ledger mutation operations | Superuser can bypass application controls |
| Audit tampering | Rewrite refused attempt | PostgreSQL append-only trigger | CI verifies trigger installation and audit delete rejection | Database owner privileges require separation |
| Unauthorized adjustment | Admin silently changes balance | No adjustment endpoint exists yet | Feature intentionally not exposed | Controlled adjustment workflow pending |
| Sensitive data exposure | Error reveals account existence | Safe account `404` and generic auth errors | Route behavior implemented | Access logs and rate limits need review |
| Request flooding | High-volume transaction requests | Deployment-level rate limiting pending | Not verified | Availability risk |
| Floating-point error | Decimal amount loses precision | API `Decimal`, PostgreSQL `NUMERIC` | Schema and migration reviewed | Currency scale policy needs explicit enforcement |
| Currency mismatch | Cross-currency transfer | Currency equality check | Service logic implemented | FX support is not implemented |
| Deadlock | Opposite transfers lock accounts differently | Deterministic account ID ordering | CI runs opposing-direction transfer test | Serialization retries need implementation |
| Projection drift | Balance differs from ledger | Atomic projection update and future reconciliation query | Reconciliation endpoint pending | Manual database intervention |
| Audit loss on rollback | Refusal disappears with transaction rollback | Refusals are committed before raising | Service path implemented | Database outage cannot guarantee audit persistence |
| AI unauthorized posting | Model directly moves money | AI has no transaction authority by design | Architectural constraint | Future integrations must preserve this boundary |
